Files in your project

Open the docs/operations/registration-cleanup/ folder:

  • README.md — complete operator instructions, recovery guidance, and limitations.
  • cleanup.sql — single guarded PostgreSQL statement; defaults to a rehearsal that rolls back every proposed deletion.
  • verify.sql — read-only checks for before and after execution.

Operator checklist

  1. Review the full README. Confirm the removal scope, including all contributions and poll votes. Never add this SQL to publishing or application startup.
  2. Select Production in Replit's Database tool. Arrange a no-writes maintenance window and drain in-flight application and organizer requests. Closing public registrations alone is insufficient.
  3. Verify a restorable production backup or restore point. Record its timestamp and recovery procedure securely. A registration CSV or ordinary code checkpoint is not a substitute. Do not put private backups or credentials in chat, the repository, or public assets.
  4. Run the entire cleanup.sql statement unchanged for a rehearsal. Use autocommit; if the SQL client opens a transaction, roll it back after rehearsal to release the table locks. Expect REHEARSAL PASSED … Nothing removed.
  5. Stop on any changed-data, dependency, permission, or lock error. Do not bypass the safeguards. New registrations, contributions, votes, or payments require an updated review.
  6. Only after backup and scope approval, follow the README to enable apply mode and enter the exact approval phrase. Execute the complete statement once. Success is atomic; errors roll back the cleanup.
  7. Run verify.sql before resuming traffic. Expect zero registrations and attendees, zero contributions and votes, zero fund balance, and unchanged users/settings. Reload the organizer registrations page.

After cleanup

The registration list should show No registrations found. The current UI disables CSV export for an empty list; the authenticated export endpoint returns only the header. New registrations will appear normally and use continuing ID numbers, not restart at 1.

If recovery is needed after commit, keep traffic paused and use the verified production restore procedure. A whole-database restore also rewinds unrelated changes after the restore point.

Validation performed

The SQL passed 18 scenarios in a disposable, socket-only local PostgreSQL database: rehearsal rollback, approval guards, exact deletion and preservation, replay refusal, changed/new records, mixed payments, changed foreign keys, cross-schema dependencies, triggers, and rollback after a late failure. Neither production nor the project development database was used for those tests.
